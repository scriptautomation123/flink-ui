ok, but this will be a multi tenant cluster, how do i protect one set of job configs from another set of job configs?


googlesearch response

Because you are running a single shared Session Mode cluster without an operator, achieving strong multi-tenant security is fundamentally difficult. In a standard Flink Session cluster, all jobs share the same JVM processes (JobManager and TaskManagers) and run under the exact same Kubernetes ServiceAccount.

This means if you mount separate tenant secrets (like truststores) into the cluster, Tenant A's running job can technically access Tenant B's mounted secrets or read other tenants' configuration parameters via JVM environment inspections or Java's reflection.

To protect distinct sets of job configurations from one another in this architecture, you must implement the following safeguards:


1. The Hard Truth About Flink Session Mode

A Flink Session cluster does not have a native multi-tenant authorization boundary at the job execution level.

Anyone with network access to the Flink REST API (flink run) can see all running configurations.
Any job code executing inside the TaskManager has equal access to the local container filesystem and memory space.

The Best Practice Alternative: If absolute cryptographic or configuration isolation is required between tenants, you should move away from a shared Session cluster and deploy Flink Application Mode. In Application Mode, each tenant gets their own dedicated JobManager and TaskManager Pods inside isolated OpenShift Namespaces, perfectly separating OpenShift Secrets, ConfigMaps, and configurations.

If you must remain in a shared Session Mode cluster, apply the strategies below.


2. Isolate Configuration File Delivery (CI/CD Pipeline Separation)

Do not store multiple tenant configuration files or sensitive properties directly inside the TaskManager Pods. Instead, make the deployment pipeline the gatekeeper:

Role-Based Access (RBAC) in CI/CD: Ensure Tenant A's engineers only have access to Tenant A's Git repository and pipeline (e.g., Tekton, Jenkins, or GitLab CI).


Inject Secrets via Pipeline Environment Variables: Keep passwords, DB keys, and connection strings inside tenant-isolated pipeline environments. When the pipeline calls flink run, pass these configurations strictly as ephemeral program arguments rather than static files:

bash

# This runs inside Tenant A's isolated CI/CD worker flink run -m flink-route.apps.cluster.domain:443 /jars/tenant-a.jar \   --db.password "${TENANT_A_SECRET_PASS}" \   --kafka.username "tenant-a-user"

Use code with caution.

3. Namespace-Scoped Object Storage for Files & Stores

If your jobs require distinct keystores, truststores, or heavy .properties files that cannot be converted to plain string arguments, do not mount them directly to the TaskManager storage volume. Use secure cloud/on-prem object storage (like an isolated MinIO bucket, AWS S3, or an internal secure file server) to act as a secure proxy.

Secure the Object Storage: Provision separate folders/buckets per tenant and secure them with discrete access keys.


Fetch Files Ephemerally via Flink Distributed Cache: When submitting the job, use Flink’s pipeline.cached-files configuration:

bash

flink run \   -m flink-route.apps.cluster.domain:443 \   -D pipeline.cached-files="tenant_truststore,s3://tenant-a-secure-bucket/certs/truststore.jks" \   /jars/tenant-a.jar

Use code with caution.


Flink will automatically stream that specific truststore file from the bucket straight into the TaskManager slot execution directory when Tenant A's job boots up, limiting cross-tenant exposure.

4. Implement Code-Level Namespacing & Class Isolation

Because jobs run in the same cluster, bad or malicious code from one tenant can interfere with another. Flink separates job classes using child-first classloaders, but you should mandate code patterns to protect configurations:

Shaded Connectors: Ensure each tenant jar shades its respective dependencies (like Kafka or PostgreSQL drivers). If Tenant A and Tenant B use different versions of a secure client connector, shading prevents cross-contamination of client configurations inside the JVM class path.
Encrypted Program Arguments: If you are highly concerned about a rogue user viewing other jobs' configurations in the plain-text Flink Web UI, encrypt your sensitive configuration properties before executing flink run. Have the job decrypt the properties inside its open() method using a key pulled securely from an external key vault (such as HashiCorp Vault or CyberArk) using a specific AppRole credential passed to the job.

To solve your core challenge—versioning your configurations alongside your code while keeping secrets safe—you should adopt a "Pointer-to-Vault" architecture using GitOps principles.

Here is exactly how to design and execute this workflow.


1. The Strategy: Separate "Structure" from "Secrets"

In Git (Versioned with Code): Store your application properties file (application.conf, config.yaml) directly in your code repository. However, replace all sensitive values, truststore passwords, and keys with Vault paths or placeholders.
In Vault (Secure Engine): Store the actual passwords, keys, and base64-encoded truststores/keystores. Version control them using Vault's KV V2 engine or a secure Git-backed infrastructure-as-code repo (like Terraform).

Example: Your Versioned config.yaml in Git

yaml

Because you are running in a shared Session Mode cluster without an operator, you must give your job a way to prove its identity to Vault when it boots up.

Authentication: When you execute flink run, pass a low-privilege, short-lived Vault Token or an AppRole RoleID/SecretID as a command-line parameter.
Bootstrap (open method): Inside your Flink application, before initializing your sources or sinks, connect to Vault using the token, read your versioned config.yaml, and swap the placeholders with real secrets.

Tenant Isolation: If Tenant B attempts to inspect Tenant A's running job configuration in the Flink Web UI, they will only see the command line arguments. Since the Vault token expired 10 minutes after submission, Tenant B cannot use it to steal Tenant A's secrets.
